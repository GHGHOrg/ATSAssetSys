DECISION MADE
Option 1: keep working on a single spec.md until the user says "final".
Then decide whether to split, using the approach below.

WHY NOT SPLIT NOW
- Design is not finished. The v52 rework (groups 1 to 3) and the consistency-check
  findings (1 to 7) are applied. What remains is the user's approval of spec.md as a
  whole ("final").
- One file means one approval gate (Ruleset A: approve spec.md before Build).
- The file (408 lines) is small enough to review in one sitting. Context-window fit has
  not been measured.

SPLIT RULES
1. Never separate sections 3, 4 and 5. Deletion (4.7) depends on 4.1, 4.2 and C5, and
   the examples test those rules. Reversals (4.6) also depend on 4.1 and Example D.
2. Keep the concerns table (C1-C18) in the index. Other files cite concerns by ID
   (for example "see C7") and rule numbers (for example "see 4.1").
3. Move text without changing it. Replace each moved section in the index with a
   pointer. Any content change is a separate, visible edit.
4. Do not split by build slice. Rules cut across slices. Each slice file in the plan
   cites the spec sections it needs instead.
5. Keep section numbers and concern/example/component IDs (C, A to G, K) stable so
   references in other files stay valid.
6. Section 14 rule 1 (every write goes through K1) must stay visible in the index,
   because the restore and entry-flow files both depend on it.
7. spec/example-import.csv is STALE: it describes the CSV import that v52 removed, and
   spec.md no longer refers to it. It is replaced by spec/example-backup.csv,
   spec/example-backup-expected.md and spec/template-backup.csv (section 8). The old file
   stays unchanged until you remove it. If the format changes, update section 8 (or
   spec/backup-restore.md) and the three sample files together.

MINIMAL ALTERNATIVE (recommended if a split is wanted)
Split out only spec/backup-restore.md. Section 8 is about 83 lines now (it was 31 before
the file format was written, and about 50 as the old CSV section), the second-largest
block after sections 3 to 5. Its content is settled (D5 and D6 are resolved). It cites
4.1 to 4.6, 4.9, C3, C7, C8, C13 and C16 by ID. Keep everything else in spec.md. If done
before "final", the user approves the index plus that file. The case for splitting is
stronger than before, because section 8 grew as expected.

TRIGGERS FOR SPLITTING
- The user asks for it, or
- spec.md becomes uncomfortable to review in one sitting, or
- a section keeps growing (section 8 did grow, from 31 to 83 lines once D5 was written), or
- the plan slices are worked one at a time and the full spec no longer fits comfortably
  next to the code in context.

AFTER A SPLIT
- Re-confirm cross-references (C-IDs, K-IDs, rule numbers, example letters, section
  numbers).
- The user re-approves the index, since the approved file changes shape.
- plan.md slice files cite specific spec sections (for example "slice 4 uses 4.1, 4.2,
  4.6, 4.7 and Example E").
